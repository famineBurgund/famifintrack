# 08 — Роадмап

Этапы идут последовательно. Каждый заканчивается работающим вертикальным срезом, который можно потрогать руками. Kafka и k8s намеренно появляются не в начале: сначала нужна работающая логика, потом распределённость.

## Этап 0. Фундамент
- [ ] Структура репозитория по [02-architecture.md](02-architecture.md#структура-репозитория)
- [ ] Исправить импорт: `github.com/go-chi/chi/middleware` → `github.com/go-chi/chi/v5/middleware`, убрать chi v1 из `go.mod`
- [ ] Вынести пароль БД из `config.yaml` в env, добавить `config.example.yaml`, `config.yaml` и `.env` — в `.gitignore`
- [ ] `internal/platform`: config, logger (slog), postgres (pgxpool + tx manager), httpx, graceful shutdown
- [ ] `docker-compose.yml` с Postgres и Redis, Makefile
- [ ] golang-migrate: каталоги, команды make
- [ ] CI: lint + test

**Готово, когда:** `make up && make run-gateway` поднимает сервис с `/healthz` и `/readyz`, логи пишутся в slog, CI зелёный.

## Этап 1. Auth
- [ ] proto `auth/v1`, `buf generate`
- [ ] Миграция `users`
- [ ] Register / Login (argon2id), `username` с проверкой уникальности, JWT access, refresh в Redis с ротацией и детектом reuse
- [ ] Rate limiting входа
- [ ] gateway: REST `/auth/*`, `/me`, JWT-middleware, проброс `x-user-id` в gRPC metadata
- [ ] Тесты: unit на токены, integration на репозиторий

**Готово, когда:** через curl можно зарегистрироваться, войти, обновить токен и выйти. Повторный refresh старым токеном отзывает сессии.

## Этап 2. Счета, категории и транзакции
- [ ] Миграции `accounts`, `account_members`, `categories` (с триггером и `user_id | account_id`), `transactions` (с `account_id`, `created_by`, `paid_by`, `kind`)
- [ ] Только **личные** счета, но через `account_members` и проверку доступа `access.Role`. Тогда совместные счета на этапе 6 не потребуют переделки
- [ ] Личный счёт «Основной» и категории по умолчанию. **Временно** создаются синхронным gRPC-вызовом из auth, на этапе 3 их заменит событие
- [ ] CRUD категорий со всеми инвариантами, архивация
- [ ] CRUD транзакций, фильтры, курсорная пагинация, переводы между своими счетами
- [ ] Тесты изоляции счетов
- [ ] **Фронт:** логин и регистрация, переключатель счёта, список и форма транзакций, дерево категорий

**Готово, когда:** в UI можно завести несколько личных счетов и транзакции в категории третьего уровня, а чужие данные недоступны.

> Счета и `account_id` вводятся сразу, а не вместе с соцфункциями, потому что потом пришлось бы переписывать схему, все запросы, события (ключ партиции) и агрегаты.

## Этап 3. Kafka, analytics, главный отчёт
- [ ] Kafka в docker-compose, `internal/platform/kafka` (producer, consumer group, DLQ)
- [ ] Outbox + релей в auth и finance
- [ ] `user.registered` → личный счёт и категории по умолчанию (убрать временный вызов)
- [ ] analytics: консьюмеры `finance.accounts.v1` (реплики счетов и участников) и `finance.transactions.v1`, `daily_aggregates`, `processed_events`
- [ ] `GetSummaryReport`: итоги, сравнение с прошлым периодом, разбивка по дереву, серия, топ-5
- [ ] Кеш отчётов в Redis с версионированием
- [ ] `RebuildAggregates` + `StreamTransactions`
- [ ] **Фронт:** дашборд с выбором периода, графики

**Готово, когда:** новая транзакция появляется в отчёте за пару секунд, а повторная доставка события не искажает суммы.

## Этап 4. Финансовые цели
- [ ] Миграции `goals`, `goal_contributions`
- [ ] CRUD целей, ручные взносы, взносы через транзакции `savings`
- [ ] Автоматический переход в `achieved` и обратно
- [ ] Расчёт `required_monthly` и `on_track`
- [ ] События `finance.goals.v1`
- [ ] **Фронт:** страница целей с прогрессом

## Этап 5. Рекомендации
- [ ] Движок правил и конфиг порогов
- [ ] Правила из [03-domain.md](03-domain.md#рекомендации), каждое с табличными тестами
- [ ] Встраивание в отчёт + эндпоинт `/recommendations`
- [ ] **Фронт:** блок рекомендаций с «почему» (facts), дисклеймер

**Готово, когда:** на тестовом наборе данных (seed-скрипт с данными за 6 месяцев) выдаются ожидаемые рекомендации.

## Этап 6. Совместные счета
- [ ] Создание совместного счёта, копирование шаблона категорий
- [ ] Роли и матрица прав (`domain/permissions.go`) + табличный тест
- [ ] Приглашения по username и по ссылке, принятие и отклонение, выход, удаление участника, передача владения
- [ ] События `finance.accounts.v1`, реплика участников в analytics
- [ ] Отчёт `scope=account`, совместные цели с вкладом по участникам
- [ ] **Фронт:** создание счёта, участники, приглашения, страница принятия по ссылке

**Готово, когда:** два пользователя ведут общий счёт, видят один отчёт, а `viewer` не может ничего изменить.

## Этап 7. Социальные функции
- [ ] social-service: каркас, миграции, консьюмеры `auth.users.v1` и `finance.*`
- [ ] Профили, аватары через MinIO (presigned URL), поиск по username
- [ ] Друзья, заявки, блокировки; `social.v1` → реплика блокировок в finance
- [ ] Лента счёта (fan-out on write), комментарии с упоминаниями, реакции
- [ ] Уведомления: таблица, настройки, Redis Pub/Sub, SSE в gateway с `Last-Event-ID`
- [ ] Лента друзей с opt-in шарингом достижений
- [ ] **Фронт:** профиль, друзья, лента, комментарии, центр уведомлений

**Готово, когда:** комментарий в общем счёте приходит второму участнику в реальном времени, а после переподключения пропущенные уведомления догружаются.

## Этап 8. Разделение расходов
- [ ] `split_mode`, `transaction_splits` с триггером суммы, `paid_by`
- [ ] Расчёт балансов и упрощение долгов
- [ ] Расчёты (`settlement`) с подтверждением получателем
- [ ] `daily_share_aggregates` и `include_shared` в личном отчёте
- [ ] Правила `shared_debt_open`, `shared_share_high`
- [ ] **Фронт:** форма сплита, страница «Кто кому должен»

**Готово, когда:** для трёх соседей с тратами в разных пропорциях балансы сходятся в ноль, и после расчёта долг исчезает.

## Этап 9. Kubernetes
- [ ] Dockerfile (multi-stage, distroless), образ фронта
- [ ] Манифесты по [06-infrastructure.md](06-infrastructure.md#kubernetes), migrate-Job
- [ ] Локальный кластер kind/k3d, ingress
- [ ] gRPC-балансировка через headless Service
- [ ] Kustomize или Helm

**Готово, когда:** `make k8s-up` разворачивает всё приложение в локальном кластере, rolling update проходит без ошибок у клиента.

## Бэклог (после MVP)
- Импорт CSV-выписок с маппингом на категории
- Регулярные транзакции (подписки, зарплата)
- Бюджеты-лимиты на категорию в месяц + правило «превышен лимит»
- Мультивалютность с курсами
- Экспорт отчёта (CSV / PDF)
- Push и email-уведомления (вынести доставку из social в отдельный notification-service)
- Совместные бюджеты-лимиты с уведомлением всех участников при превышении
- Групповые челленджи между друзьями («месяц без доставки»), без раскрытия сумм

# 01 — Продукт и требования

## Цель

Дать пользователю простой инструмент, который отвечает на три вопроса:

1. **Куда уходят деньги?** — учёт доходов и расходов по иерархии категорий.
2. **Как у меня дела за период?** — сводный отчёт за любой выбранный промежуток.
3. **Что делать дальше?** — цели накоплений и понятные рекомендации по тратам.
4. **Как вести деньги вместе?** — совместные счета с семьёй или друзьями, общие цели, разделение расходов и лёгкие социальные функции.

Проект учебный: архитектура намеренно включает gRPC, Kafka и Kubernetes, чтобы отработать их на реальной задаче. Там, где это усложняет жизнь без пользы, в документах прямо сказано, что можно упростить.

## Роли

| Роль | Описание |
|---|---|
| Гость | Может зарегистрироваться и войти |
| Пользователь | Владеет личными счетами, состоит в совместных счетах, имеет профиль и друзей |

Внутри совместного счёта у пользователя есть роль: `owner`, `editor` или `viewer`. Матрица прав — в [09-social.md](09-social.md#роли-и-права). Админки в MVP нет.

## Функциональные требования

### FR-1. Регистрация и авторизация
- Регистрация по email и паролю. Email уникален (без учёта регистра).
- Вход возвращает пару токенов: короткоживущий access (JWT) и долгоживущий refresh.
- Обновление пары по refresh-токену с ротацией: старый refresh после использования недействителен.
- Выход отзывает текущий refresh-токен. Опционально: «выйти на всех устройствах».
- Защита от перебора: ограничение числа попыток входа по IP и по email.
- В профиле хранятся часовой пояс и базовая валюта: от них зависят границы периодов в отчётах.
- При регистрации задаётся уникальный `@username`, по нему пользователя находят друзья и приглашают в счета.

### FR-1a. Счета
- Транзакции и цели всегда принадлежат **счёту**. Счёт бывает личный (`personal`, один владелец) или совместный (`shared`, до 10 участников).
- При регистрации создаётся личный счёт «Основной». Пользователь может завести ещё личные счета, например «Карта» и «Наличные».
- Между своими счетами можно делать **переводы**, в том числе пополнять совместный счёт с личного. Переводы не входят в доходы и расходы.
- Совместные счета, приглашения, роли и разделение расходов описаны в [09-social.md](09-social.md) (FR-7 – FR-9).

### FR-2. Категории (до 3 уровней)
- Категория имеет тип: `income` или `expense`. Дочерняя категория наследует тип родителя.
- Максимальная глубина — 3 уровня, например `Еда → Рестораны → Кофе`.
- При регистрации пользователю создаётся набор категорий по умолчанию. Их можно переименовывать, архивировать и дополнять.
- Личные категории общие для всех личных счетов пользователя. У каждого совместного счёта свой набор категорий.
- Категорию, в которой есть транзакции, нельзя удалить физически: её можно только архивировать.
- Корневая категория расходов помечается классом бюджета (`needs` / `wants` / `savings`), это нужно для рекомендаций.

### FR-3. Транзакции
- Поля: счёт, категория, сумма, дата и время операции, комментарий. Автор записывается автоматически.
- Тип (доход или расход) определяется категорией и отдельно не вводится.
- CRUD, список с фильтрами (период, категория с поддеревом, тип, поиск по комментарию) и курсорной пагинацией.
- Транзакцию можно привязать к категории любого уровня, не обязательно к листу.

### FR-4. Главный отчёт
Пользователь задаёт период `[from, to]` (произвольный или пресет: неделя, месяц, квартал, год) и набор счетов. По умолчанию берутся все личные счета; можно выбрать один совместный счёт или добавить к личным свою долю трат в совместных. В ответ он получает:
- суммарный доход, расход и разницу (net);
- норму сбережений: `net / income`;
- разбивку по категориям с раскрытием дерева и долей каждой категории;
- динамику по дням, неделям или месяцам (гранулярность выбирается автоматически или вручную);
- сравнение с предыдущим периодом такой же длины;
- топ-5 категорий расходов;
- блок рекомендаций для этого периода (см. FR-6).

### FR-5. Финансовые цели
- Цель: название, целевая сумма, необязательный дедлайн.
- Прогресс складывается из взносов. Взнос можно добавить вручную или автоматически из транзакции в категорию класса `savings`, связанную с целью.
- Для цели с дедлайном рассчитывается рекомендуемый ежемесячный взнос и признак «успеваю / не успеваю» с учётом среднего свободного остатка.
- Статусы: `active`, `achieved`, `archived`.
- Цель принадлежит счёту. Цель совместного счёта общая, с разбивкой вклада по участникам (FR-8).

### FR-6. Рекомендации
Рекомендации строятся детерминированными объяснимыми правилами, без ML. Каждая содержит текст, важность и цифры, на которых она основана. Список правил с порогами — в [03-domain.md](03-domain.md#рекомендации).

Примеры:
- «Норма сбережений 4% — ниже рекомендуемых 10–20%»;
- «Расходы на "Рестораны" выросли на 45% к среднему за 3 месяца»;
- «Чтобы успеть к цели "Отпуск", откладывайте 18 000 ₽ в месяц»;
- «Подушка безопасности покрывает 1,2 месяца расходов из рекомендуемых 3–6».

> Рекомендации носят информационный характер и не являются индивидуальной финансовой консультацией. Этот дисклеймер выводится в интерфейсе.

### FR-7 – FR-12. Совместные счета и социальные функции
Совместные счета, общие цели, разделение расходов, профиль и друзья, лента с комментариями и реакциями, уведомления в реальном времени. Подробности — в [09-social.md](09-social.md).

## Нефункциональные требования

| Требование | Целевое значение |
|---|---|
| Время ответа CRUD API | p95 < 150 мс |
| Время построения отчёта за год | p95 < 500 мс (с кешем < 50 мс) |
| Изоляция данных | Каждый запрос к финансовым данным проверяет членство `user_id` из токена в счёте; проверяется интеграционными тестами по матрице ролей |
| Приватность | Друзья не видят финансовых данных; доступ к деньгам даёт только членство в счёте |
| Доставка уведомлений | В реальном времени (SSE) < 2 с; при обрыве соединения пропущенное догружается |
| Деньги | Только целые числа в минимальных единицах (копейки). Никаких `float` |
| Время | Хранится в UTC (`timestamptz`), периоды отчётов считаются в часовом поясе пользователя |
| Консистентность отчётов | Eventual: отчёт отражает новую транзакцию не позже чем через ~5 с |
| Наблюдаемость | Структурные логи (slog JSON), метрики Prometheus, сквозной `request_id` / trace id |
| Безопасность | Пароли хешируются argon2id, секреты только через env или Secret, HTTPS на ingress |

## Вне скоупа MVP

- Несколько валют в одном отчёте и конвертация (в MVP одна базовая валюта на пользователя).
- Синхронизация счетов с банками; остатки счетов ведутся только по введённым транзакциям.
- Импорт банковских выписок (CSV, OFX) — кандидат на этап после MVP.
- Личные сообщения и чаты (есть только комментарии внутри совместного счёта).
- Публичные профили с финансовыми данными, рейтинги, сравнение с другими пользователями.
- Push и email-уведомления (только in-app и SSE).
- Регулярные (повторяющиеся) транзакции и бюджеты-лимиты по категориям — кандидаты на этап после MVP.
- Мобильное приложение.

## Глоссарий

| Термин | Значение |
|---|---|
| Транзакция | Факт дохода или расхода с суммой, датой и категорией |
| Категория | Узел дерева глубиной до 3, определяет тип транзакции |
| Класс бюджета | `needs` (обязательные), `wants` (желаемые), `savings` (сбережения) — метка корневой категории расходов |
| Net | Доход минус расход за период |
| Норма сбережений (savings rate) | `net / income` за период |
| Подушка безопасности | Сумма накоплений, выраженная в месяцах средних расходов |
| Минорные единицы | Сумма в копейках (центах): 1 ₽ = 100 |
| Счёт | Контейнер для транзакций и целей: личный (`personal`) или совместный (`shared`) |
| Участник | Пользователь, состоящий в совместном счёте с ролью `owner` / `editor` / `viewer` |
| Перевод | Перемещение денег между счетами; не доход и не расход |
| Сплит (split) | Разделение траты совместного счёта на доли участников |
| Расчёт (settlement) | Транзакция возврата долга между участниками |
| Лента | Поток событий совместного счёта или достижений друзей |
